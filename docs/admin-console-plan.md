## 2. Current state

- **Apps:** `apps/web` (Next.js App Router, customer UI and API), `apps/worker` (BullMQ on Redis), and the separate `apps/admin` Next.js app. Shared code lives in `packages/{contracts,domain,data,agent,ui}`.
- **Customer auth:** Better Auth in [auth.ts](../apps/web/src/server/auth/auth.ts) uses the public `users`, `sessions`, `accounts`, `verifications` and `rateLimits` tables. Customer access checks reject deletion-requested or suspended users/workspaces. Customer MFA state is not available in the schema.
- **Admin auth:** `apps/admin` uses a separate Better Auth instance, admin-schema identity tables, staff RBAC and Cloudflare Access identity validation. The admin app and protected `/users` directory/profile are implemented locally; production gate and deployment wiring remain outstanding.
- **Authorization:** Workspace-scoped roles are Owner, Admin, Office and Field (see [authorization-engine.md](authorization-engine.md)). Separate platform staff roles are Super Admin, Support and Billing. The workspace **Admin** role is a customer role and is unrelated to platform admins.
- **Audit:** Domain-specific tables include `authorizationAudit`, `billingAudit`, `chatActionAudit` and `*ExportAudit`. Staff operations use an append-only, hash-chained admin audit ledger with a viewer/export workflow and read-only archive-health status. Production archive storage and deployment remain outstanding.
- **Knowledge:** `knowledge/operations/*.md` and `manifest.json` are seeded by the worker (`pnpm knowledge:seed`) into `helpArticles`, `helpChunks`, `helpEmbeddings` and `helpHeads` (pgvector, `text-embedding-3-small`/1536). Retrieval is filtered by workspace role, capability and plan. The isolated admin runbook corpus and assistant are not yet delivered.
- **Infra:** [.railway/railway.ts](../.railway/railway.ts) defines the application services. Split Postgres roles and the admin app's least-privilege role are implemented locally; the Cloudflare tunnel/policy, production secrets and deployment are not complete. The web pre-deploy step remains the owner of Knex migrations.
- **Runtime flags:** `CHAT_ENABLED` and `ESTIMATE_EMAIL_ENABLED` remain hard-off environment ceilings, with Admin-managed global, plan and workspace rollout flags. The flag migration is applied locally only; `BILLING_SANDBOX_ENABLED` remains environment-only.

**Gap:** The local admin console now has a dashboard and shared navigation for its integrated customer-user, workspace, data-request, staff, audit, AI-usage, read-only queue/outbox and feature-flag routes. Remaining v1 work includes full browser E2E coverage; standalone billing; global AI budgets; safe queue retry/remove and outbox resend actions; file/malware status; impersonation; and external audit archive delivery, verification, retention enforcement and alerting. Knowledge publishing and the admin assistant are deferred. Production deployment remains incomplete.

## 3. Goals and non-goals

**Goals**
- Staff can find any user or workspace, understand its state and take common support actions without direct database access.
- Every staff read of tenant data and every staff mutation is attributable, justified and auditable.
- A compromise of the customer app or a customer session cannot grant admin access, and an admin compromise has a bounded blast radius.
- Future goal (deferred): Staff can learn how the application works and how to administer it from one searchable source, with assistant help.

**Non-goals (v1)**
- Customer-facing support portal or ticketing (use an external helpdesk; the integration is a later phase).
- Write-mode impersonation (acting as the customer).
- Arbitrary SQL or data editing from the console.
- Assistant-executed admin actions (the v1 assistant is read-only and documentation-grounded; see §8).

### 5.3 Mutation path

Admin server action → staff permission check → step-up check if 🔐 → reason required → **shared use-case function in `@salesmora/data`** (for example `requestAccountDeletion`, `changePlan`, `suspendWorkspace`), which enforces the same invariants as the customer path → the domain audit row (for example `billingAudit`) **and** `admin.auditEvents` are written in the same transaction.

The admin app never writes tenant tables directly. When an admin action needs logic that currently lives in `apps/web/src/server/*`, that logic first moves into `@salesmora/data` or `@salesmora/domain`, with tests, as a refactor step.

### 5.4 Staff audit

- Each event records: `id`, `occurredAt`, `staffUserId`, `staffRole`, `action`, `targetType`, `targetId`, `workspaceId`, `reason` (required for mutations, impersonation and PII reveal), `before`/`after` (redacted JSON), `requestId`, IP, user agent and `prevHash`/`hash` (hash chain for tamper evidence).
- PII reveal events are logged too: customer email and session IPs are masked by default, and revealing them requires a reason and an audit event. Customer-user phone data is not currently stored; phone reveal is deferred until the product defines an authoritative account-phone source and collection flow.
- No `UPDATE` or `DELETE` grants on `admin.auditEvents` for any runtime role. Retention is 1 year (Q6). A worker retention task, running under a dedicated role, purges older events and records the last purged hash as a chain anchor so verification still works.
- A separate audit-only worker will run nightly and export all newly appended events through a captured sequence bound (NDJSON plus a chain checkpoint) to a dedicated Cloudflare R2 bucket with a 1-year bucket lock, so the database cannot be the only copy. Selection is by sequence, not occurrence date, to include late/backdated appends. Dedicated bucket-scoped object read/write credentials stay in the isolated archive runtime, not either web app or the customer worker. This supersedes the earlier write-only-token assumption: standard R2 token presets do not offer write-only access. Independent object/configuration checks need separately scoped read authority; their exact deployment boundary remains part of the upcoming integration design. Privileged Cloudflare administrators can change lock rules, so R2 bucket locks are not irrevocable compliance-mode storage.
- Customer-visible transparency: workspace Owners see every impersonation session, including break-glass, in Settings → Support access (Q4).

### 5.5 Other controls

- Restricted Stripe key for the admin app (read customers, subscriptions and invoices; write only the operations used by B3/B4). Refunds are a link-out to the Stripe dashboard.
- Secrets are only in Railway variables, never `NEXT_PUBLIC_`. They are validated at startup like `requiredEnv` in the web app.
- Dependency and container scanning in CI for `apps/admin`. Alerts fire for staff sign-ins from new devices, MFA resets, role grants, flag changes in production, and bulk actions.
- No CSV export of tenant data from the console in v1, apart from audit log export for Super Admin.

### W4 live integration plan and local implementation (approved)

**Existing foundations:** `admin.workspaces.ownership.transfer` is already a code-owned Super Admin-only permission. The least-privilege admin database grants already include the ownership columns, membership-role updates, authorization audit insert, and ownership-notice outbox writes. `transferWorkspaceOwnership` in `packages/data/src/workspaces/team-actions.ts` already locks the workspace, rejects deletion-pending workspaces, requires an existing verified active member who does not own another workspace, swaps `workspaces.ownerId` and membership roles atomically, queues one notice for each person, and records the domain audit. A deferred database invariant requires exactly one matching Owner. The ownership-notice worker and email template already send both messages without the staff reason or an app link. The isolated data rehearsal covers eligibility, deletion, atomicity, audit, notices and retry behavior.

**Approved design and implementation:**

1. Add strict contracts for action methods, start (workspace, selected member, expected current Owner, and 10–500 character reason), factor verification and commit/result. ## 7. Read-only impersonation design

Recommended: **admin-rendered views, not minted customer sessions.**

- The admin app renders the workspace's leads, customers, jobs, estimates, work orders and calendar using shared `packages/ui` components and **read** repositories from `@salesmora/data`. An `AuthorizationContext` is built for the chosen member role, so staff see exactly what that role sees.
- No customer session cookie is created, and the customer app's write paths are never reachable. Read-only behavior is structural: the admin DB role has no `UPDATE` grants on those domain tables.
- `admin.impersonationGrants` stores the consent source, granting owner or break-glass approver, scope, start and end times, reason and ticket. Every page view writes `admin.auditEvents`.
- Trade-off: some customer screens are not reproduced pixel-for-pixel. This is acceptable for support, safer than session minting, and does not modify the customer auth path.

### 8.3 Admin assistant

- **Isolated corpus:** a new `admin.knowledge*` table set, seeded by a worker task (`pnpm admin-knowledge:seed`) that reuses `packages/data/src/knowledge` ingestion and embeddings. The tables are separate, rather than sharing `helpArticles` with a flag, so the customer assistant cannot retrieve staff docs even if a query bug occurs.
- **v1 = read-only RAG.** The assistant answers "how do I…/why does…" questions with hybrid retrieval (vector + full-text) filtered by staff role. Every answer cites runbook anchors. If nothing relevant is retrieved, it says "not documented" instead of guessing.
- **No tenant data is sent to the model in v1.** Prompts contain only staff questions and doc chunks, and a PII scrubber runs on the staff input. Usage is recorded in `aiUsageCalls` under a platform scope (Q9). The assistant uses `ADMIN_CHAT_MODEL` (default: the same model as `CHAT_MODEL`), `text-embedding-3-small`/1536 and a **separate OpenAI project key** (`ADMIN_OPENAI_API_KEY`). The monthly budget defaults to 1M tokens and is editable in system settings (F3). When the budget is exhausted, the assistant stops answering, but docs and full-text search keep working.

- **Freshness:** a CI check fails when `lastReviewed` is older than 180 days for pages whose `appliesTo` features changed, and when generated reference files are stale. Retrieval quality is tracked with a small `admin-knowledge:evaluate` question set.
