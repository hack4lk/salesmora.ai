# Shared assistant Leads module

Implemented locally October 16, 2026 after approval of the shared capability approach. This refactors existing pipeline counts, lead creation and stage changes into two model-facing functions. It does not automatically implement every planned lead action.

## Contract and execution

`packages/contracts/src/lead-capabilities.ts` is the implemented operation catalogue. An entry defines its validation schema, model-facing function, read/draft kind, relevant page surfaces, required application permissions and description. Current entries are `history`, `details`, `search`, `pipeline_summary`, `create`, `update`, `update_with_stage`, `assign`, `add_note`, `set_archived`, `export_csv`, `delete` and `change_stage`. Strict request envelopes contain `request.operation` and `request.input`. They never accept workspace identity, role, policy, raw SQL, arbitrary columns or a model-confirmed decision.

`packages/agent/src/leads/authorization.ts` evaluates catalogue requirements against fresh application authorization. Capability availability checks an eligible record grant; actual target/field authority is enforced again by the data use case. `availableLeadOperations` returns only currently implemented and permitted operations for the surface. A shared function being available never authorizes all its operations.

`packages/agent/src/leads/tools.ts` exposes `leads_query` and `leads_propose_action`. Provider JSON schemas are generated from the same validation contracts and contain only currently permitted branches. For a default Field user, the proposal function can describe `change_stage` without exposing the `create` input branch. Help retrieval remains its separate permission-filtered tool. The old per-operation model definitions are removed.

The common graph passes current operation availability into both planning and answering. It validates the operation envelope and rechecks operation authority before dispatch, as well as retaining stream/source authorization checks and the one-proposal-per-turn bound. The model receives no commit tool. Missing operations remain unavailable even if the model requests them or a prior message claims access.

`apps/web/src/server/chat/leads/index.ts` is the exhaustive operation dispatcher. Its small adapters call existing pipeline reads, create proposals and stage proposals; they do not generate SQL or duplicate business mutation logic. Preparation reloads the user's permissions inside its workspace transaction. Existing explicit confirmation endpoints, proposal formats, hashes, expiry, record versions, idempotency, source checks, audit and shared manual data use cases stay in force. Stored proposals and transcripts require no migration.

## Pages and global behavior

All live instances use the same ConnectedAssistant and server runtime:

| Surface | Implemented operations before role filtering | Context |
|---|---|---|
| Home | history, details, search, pipeline_summary, create, update, update_with_stage, assign, add_note, set_archived, export_csv, delete, change_stage | Explicit lead UUID/LD-number required for stage changes |
| Leads list | history, details, search, pipeline_summary, create, update, update_with_stage, assign, add_note, set_archived, export_csv, delete, change_stage | Counts use authorized current filters; stage target must be explicit |
| Lead details | history, details, search, pipeline_summary, create, update, update_with_stage, assign, add_note, set_archived, export_csv, delete, change_stage | A saved server-resolved current record can supply “this lead” |
| New lead | create | Preserves the focused creation screen |
| Settings, Billing, Account, AI usage, Notifications | None; help only | Existing settings surface restriction is preserved |
| Permissions | None; help only | Existing permissions surface restriction is preserved |

Home and Leads do not require separate tool implementations or page changes. The refactor is shared, while relevance and record context remain surface-specific. Adding a new page needs an explicit surface/context decision; it cannot acquire arbitrary operations by rendering the launcher.

## Adding another operation

1. Add its strict business input contract and capability entry, including surface and permission requirements.
2. Add the matching server operation adapter to the exhaustive dispatcher, reusing the manual application use case and its record/field checks.
3. For writes, connect a typed proposal/confirmation executor and the approved review presentation. Prefer shared before/after presentation where appropriate; deletion/export retain their specialized confirmation/download needs.
4. Test operation/surface/role boundaries, target scope, input rejection and side effects. New catalogue entries must not be registered before their handlers and confirmation flows exist.

The tool names, runtime entry points and page integrations then stay the same. History and team timeline reads use the history operation, with explicit activity/notes mode. Bulk actions and job handoff remain deferred. No second LLM, generic database executor, environment change or staging deployment is introduced by this refactor.
