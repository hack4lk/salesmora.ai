# Permissions page design

October 12, 2026. Design approved; the editor is connected to the local app at Settings → Permissions.

Preview: http://127.0.0.1:6006/?path=/story/settings-permissionspage--default

The Owner-only editor uses the existing permission catalog, role ceilings, default policy, and pure policy validator. Owner, Admin, Office, and Field are selectable roles within the editor. Non-Owner viewers receive an access-required state without any controls. This presentation guard is not server authorization.

Permissions are grouped by feature with searchable labels, switches, and access-scope selectors. Protected Owner powers cannot be switched off. Permanent role restrictions remain disabled. Unreviewed and unavailable features display stored grants for reference but cannot be changed; the preview fixture uses the current live feature registry. Enabling a grant never activates an unavailable feature.

Drafts span roles. Reset defaults changes only the selected role's editable grants; discard restores the loaded policy. Dependency validation blocks review until the draft is valid. Review lists every changed role and permission with before/after scopes. Saving receives the expected revision and a proposed next revision. Double submissions are blocked. Save failures retain the draft. Stale saves require an explicit reload that warns it discards the draft. Identity confirmation uses an injected callback and retains pending changes. A successful response is validated before replacing local state.

Source, copy/fixtures, and 19 interaction stories are colocated in `apps/web/src/features/settings/permissions-page/`. `scripts/check-permissions-stories.mjs` runs each story at 1440px and 320px, checks its completed interaction state, runs Axe WCAG A/AA checks, detects horizontal overflow, and captures review screenshots. Storybook callbacks use fictional data and never call the permission store.

The Permissions sub-page is `/settings/permissions?workspace=<id>`. The main `/settings?workspace=<id>` route remains a separate Settings overview with saved business details and an Owner-only Manage permissions link. The main menu opens this overview; Permissions includes Back to Settings and preserves the workspace in both directions.

Settings navigation and its page require `settings.business.read` or protected `permissions.read`. Owner/Admin have business-read access by default; Admin cannot see the Permissions link or access its page/API. Office/Field are denied Settings under their defaults. The business profile DTO and services are loaded under the shared workspace authorization lock with current membership and policy checks. An Owner whose business-read grant is disabled can still reach permission administration without seeing business profile details. Business editing remains unimplemented; the overview displays saved fields read-only. Permissions page requests independently reload current authority; non-Owners receive a 404 without policy data.

`GET /api/permissions?workspace=<id>` returns the current policy only to its Owner, with `Cache-Control: no-store`. `POST /api/permissions` accepts the strict shared `PolicyChange` contract and rejects wrong/missing Origin, missing sessions, invalid payloads, wrong workspace, invalid dependencies, protected grants, role-ceiling violations and edits to unavailable or unreviewed features. The adapter compares the policy version before checking feature changes; the existing persistence transaction reloads current Owner authority and compares versions again under the exclusive workspace lock. Grants, incremented revision, and before/after audit entry commit together. Concurrent or replayed saves return 409 instead of duplicating writes.

Saving requires a session created less than **15 minutes** ago. A stale session returns 428. Confirm identity opens a native modal using the shared password field; the existing rate-limited sign-in endpoint verifies the fixed account email/password and issues a fresh session. The dialog clears the password, retains the permission draft, and requires another explicit Save. Failed confirmation and Cancel retain the draft. Session creation time is checked on the server; browser flags and session refresh time cannot satisfy the requirement. Current workspace authority is still checked after confirming identity.

Six isolated browser/API scenarios cover successful persistence and audit contents, immediate Office create denial, all non-Owner roles and other tenants, malformed/forged/protected/unavailable changes, concurrent/replayed saves, explicit conflict reload, stale authentication with failed/cancelled/successful confirmation, and ownership revocation after page load. The live screen and confirmation dialog also receive Axe and 320px layout checks. Test fixtures use only the isolated `_test` database. No migration or automatic changes to existing development policy are required; live policies change only on explicit Save.

Audit-history browsing, ownership transfer UI and broader cross-tab invalidation remain separate follow-ups. No additional permission-management or chat features are enabled by this integration.
