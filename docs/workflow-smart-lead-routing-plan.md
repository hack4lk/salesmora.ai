Geographic matching is an optional filter before assignment, using each selected member's saved work ZIP codes. It can be combined with either team distribution method.

- “Take turns assigning new website leads to Alex Parker and Morgan Ellis.”
- “Assign new website leads to whoever has the fewest open leads in this team.”
- “Route website leads to teammates who cover the lead's ZIP code, taking turns.”

The assistant resolves actual workspace sources and teammates, asks only for missing choices, and prepares the existing concise review. It uses member coverage saved in Settings → Team. ## Job and intake postal data

Require a structured ZIP/postal code for every newly created Job, including manual creation, estimate conversion and supported API/assistant creation paths. Store it separately from free-text location, validate server-side, display it with work/location details, and allow edits in the Work details modal. Carry forward a validated code from the originating lead/estimate when available; otherwise collect it before creating the Job. The service-location code belongs to the Job, not necessarily the customer's billing address. Estimates/intake must retain the structured value through conversion without introducing a mandatory ZIP on every estimate draft.

Existing Jobs with no structured code remain readable and retain their bookings/owners; do not guess from addresses or fabricate a migration default. Show “ZIP / postal code needed,” collect it on the next Work details save, and require it before a new automatic assignment/booking. Existing background steps must handle this as a targeted missing-data exception, not fail the queue. Complete the legacy backfill before enforcing a database-wide NOT NULL constraint; enforce the requirement on all new Job creation immediately.

Store structured country and postal code on leads and in intake field mappings. New/edit lead forms and the contact card use the same fields. Existing free-text addresses remain; do not backfill geography by guessing. Existing capture configurations remain valid. A ZIP-matching workflow requires its published source to collect/map postal code and establish country explicitly, either as a visible configured country or a submitted structured country field. Source changes must not silently remove that prerequisite.

The initial supported country is United States, explicitly labeled in the prototype. Accept five digits or ZIP+4, retain leading zeros, and match ZIP+4 by its base five digits. Persist country `US` with structured codes; do not treat these as globally unique postal codes or claim worldwide validation. Promote the same rules into the shared contract for client/server enforcement during integration. No radius, map drawing, postcode prefixes, inferred city matching, or geocoding in this slice.

Missing, invalid or unmatched geography leaves the new lead unassigned with a concise reason in lead activity and the workflow issue state. No automatic fallback to an out-of-area teammate. Correcting geography later does not automatically reassign an existing lead; the user can assign it manually. Existing unassigned-lead reminders remain applicable.

## Automatic job scheduling uses the same coverage

Lead ownership and field-work assignment remain different decisions. Fewest open leads continues to count leads; it does not become a job-workload metric. Lead routing uses the approved team and, when enabled, member ZIP coverage. It does not treat an off-duty salesperson as unable to own a lead.

For automatic crew selection, match the Job ZIP against each candidate's work ZIP codes, then intersect with the existing service qualifications and full-duration scheduling availability, time off and bookings. Every automatically selected worker must qualify. Assigned-people booking preserves the assigned crew and checks their coverage; a mismatch raises an exception rather than replacing someone. Unknown availability or missing coverage is not automatic eligibility. Reuse these checks in cancellation replacement suggestions and recheck before confirmation so stale suggestions cannot bypass current coverage.

Roll this requirement into automatic scheduling explicitly: show affected rules/unscheduled Jobs with missing ZIP or crew coverage and a Settings → Team action. Keep already booked visits unchanged. Saving missing Job ZIP, member coverage or availability can trigger a bounded reevaluation of affected, still-pending work within its original workflow cutoff; do not enroll historical Jobs or restart expired attempts. Manual assignment/booking retains its current authority and an explicit coverage warning; member willingness is an automatic-selection constraint rather than a new blanket ban on authorized manual operations.

## Assignment rules

- Route only future newly admitted, unassigned leads from the selected source. Preserve source/default/manual owners. Do not route duplicate links, historical leads or ordinary manual lead creation.
- Take turns rotates through the explicitly selected team, skipping members who do not cover the lead ZIP when geographic matching is enabled. Keep a stable cursor per workflow, not a new cursor for every transient matching subset. Only a committed new assignment advances it; preview, failed admission, rollback and duplicate retries do not.
- Fewest open leads counts nonarchived New, Contacted and Estimate sent leads owned by each selected teammate across this workspace. Won/Lost leads do not count. This measures lead count, not job hours, revenue or predicted effort. Rotate equal-count ties fairly.
- Select only current, eligible members of the approved team. Skip unavailable members without adding replacements. If none qualify, leave unassigned and surface the issue. Calendar working hours/PTO are outside this slice.
- Keep one active routing workflow per source across old and enhanced definitions. Editing an existing single-person rule is the upgrade path. Paused rules retain their status on edit; Resume affects future admissions. No Run now or catch-up reassignment.
- Record the actual owner, workflow revision, strategy, matched postal code and member coverage revision on the assignment receipt/activity so the owner choice can be explained. Notify only that actual owner, through existing preferences and branded staff email.

## Architecture and system budget

Routing stays synchronous inside the existing website admission or Intake Review transaction. BullMQ delivers notifications after commit; it does not poll for leads or decide ownership. Use the existing workspace mutation lock to serialize candidate selection, assignment, rotation and receipts, including simultaneous website submissions. Keep assignment activity, durable notification intent and owner writes atomic and idempotent.

Use one indexed active-rule lookup for the known workspace/source, one batched membership/permission/coverage projection for the approved pool, and one grouped owner-count query only for Fewest open leads. Use indexed workspace/country/postal-code/member coverage records. Reuse the request's authorization snapshot; never authenticate each candidate. Evaluate query plans and indexes against realistic team/workspace sizes, and document measured query counts before release. Do not introduce per-workflow polling, runtime AI, external geography calls or a separate intent-classification model call. Scheduling batches qualification, coverage and availability reads instead of fetching each worker separately.

Read-only intake review must not advance rotation or reserve a teammate. Review approves the policy and selected team, explaining that the final owner is selected on admission using current saved coverage. Its fingerprint binds the source, workflow revision, submitted geography and approved team, not transient workload/cursor values. Material workflow/source/geography changes require fresh review; another lead arriving does not. Recheck membership and coverage at commit, never widen the approved team, and explain if no approved member still qualifies.

Preserve existing stored single-person definitions. Add a typed routing-policy representation for team/ZIP rules and update generic publication/eligibility/notification helpers that currently assume one recipient. Do not fabricate a recipient ID for a team. Active-source uniqueness must span both representations. Version edits and reject stale writes; define deterministic cursor initialization/reset when the approved team changes, without replaying old leads.

Cache bounded setup choices with workspace/viewer-scoped React Query keys. Form changes stay local; publication/edit is one versioned mutation with targeted invalidation. No request on each field change, repeated authentication, or full-workspace lead downloads. Team settings and source configuration mutations enforce current permissions and workspace isolation server-side. Team table summaries come from a bounded batched read, not one availability request per visible member. Reuse the existing Calendar availability cache keys and mutation path in Settings, with targeted scheduling/candidate invalidation.
