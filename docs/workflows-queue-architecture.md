# Workflow scheduling and queue operations

The per-workflow minute scan is removed from production. This implementation uses the existing Redis/BullMQ service; PostgreSQL remains the source of truth. No AI runs during scheduling or delivery, and no new browser polling or authentication lookups are introduced.

## Event and delivery path

1. Database adapters observe Lead INSERT, Estimate acceptance/decision timestamp changes, and the first successful Estimate email. They look up active workflows through the workspace/recipe/cutoff index and create unique `workflowSteps` with the reviewed weekday/time-zone due date. Later successful resends do not restart timing. There is no active-workflow cache to become stale.
2. Step and workflow-notification status changes maintain `workflowQueueOutbox` in the same transaction. The outbox has tenant-bound foreign keys, a version, availability time and next-dispatch lease. Rollback removes both schedule and handoff. Notification payloads are not sent to Redis; tickets contain only outbox UUID, workspace UUID and version.
3. PostgreSQL NOTIFY wakes a dedicated listener after commit. A bounded dispatcher claims up to 100 outbox rows using SKIP LOCKED, adds BullMQ delayed jobs in bulk, then acknowledges the exact claimed versions. A dispatcher crash or failed/uncertain Redis write leaves a recoverable lease.
4. Jobs reload current authority and eligibility through shared application services. Step completion and deduplicated notification insertion commit together. The notification's own outbox row schedules email, including persistent transport retry times. Completed, held, canceled or superseded tickets are ignored.

Multiple dispatcher instances claim disjoint batches. Workers have concurrency four per process. A renewable Redis workspace lease allows one active workflow job per workspace across instances; busy workspace jobs move back into the delayed set before reading SQL. Existing workspace transactions, row locks, unique notification keys and transport idempotency keys remain the final duplicate/race protections. Processing is at least once; SMTP Message-ID alone is not an exactly-once email guarantee.

## Recovery, retention and remaining polling

One indexed claim runs every 30 seconds per worker process, irrespective of the number of idle clients/workflows; the listener reconnects on that path. It reads only pending outbox rows whose dispatch lease expired. Initial claims reserve one minute; successful handoffs move recovery to ten minutes beyond the later of availability or dispatch. A lost Redis job can therefore be up to roughly ten minutes late, plus the recovery interval/backlog. Listener loss affects prompt wakeups, not durable recovery. Publisher/recipient access holds remain pending for later recovery without leaking record content.

BullMQ retries unexpected processor failures up to five times with exponential backoff. Email failures use the existing five-attempt persisted retry policy, producing newly timed queue tickets. Worker status reports workflow queue counts, outstanding handoffs and the hourly maintenance scheduler. Monitor failed jobs, oldest overdue pending handoff, queue lag, dispatch failures and workspace lease errors; a queue outage should alert operations rather than silently depend on reconciliation.

Hourly queue maintenance deletes completed outbox rows older than seven days in batches of at most 1,000. A full batch schedules another cleanup job after one second so backlog drains without one long transaction. Steps, lifecycle audit, manual receipts and notification history are retained. Held work can recreate its handoff when resumed.

Ordinary non-workflow Estimate activity emails still use their existing shared five-second poller, now restricted by a partial index to non-workflow rows. Other existing worker tasks retain their own schedules. No claims are made that all application polling has been removed.
